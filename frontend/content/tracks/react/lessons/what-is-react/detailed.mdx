Коротко: React описывает экран функциями, данные меняются — разметка пересобирается. Здесь тот же тезис, но уже как модель, на которой держится вся библиотека.

## UI как функция данных

Формула, которую стоит уметь сказать своими словами:

**экран = f(данные)**

`f` — ваши компоненты. Данные — пропсы и состояние (состояние будет в конце трека). Нажали «В заказ» у латте — изменилось число в памяти — React снова вызывает `CafeApp`, `Menu`, `OrderBar` и получает **новое описание** экрана.

Вы не пишете «найди span счётчика и поставь 3». Вы пишете: «если в заказе три позиции, покажи 3». Разница не косметическая. При десяти карточках ручные правки DOM разъезжаются; описание «как должно быть» остаётся одним.

## Что React сравнивает

После каждого обновления данных React не обязан выкидывать весь HTML. Он сравнивает **новое дерево элементов** с предыдущим и меняет в DOM только отличия: текст цены, класс бейджа, одну кнопку.

Это часто называют «виртуальным DOM». Для работы junior+ достаточно модели:

1. Компонент возвращает описание («хочу `h1` и две карточки»).
2. React считает описание.
3. Браузерный DOM обновляется точечно.

Не нужно вручную кэшировать узлы и не нужно бояться «React всё перерисовывает с нуля» — пересчитывается описание, не обязательно каждый пиксель.

Точная реализация менялась между версиями. Ментальная модель — нет: вы по-прежнему описываете результат, а не шаги мутации.

## react и react-dom

Пакет `react` — компоненты, элементы, хуки. Пакет `react-dom` — мост к браузеру: `createRoot`, события, обновление DOM.

Поэтому в `main.jsx` пишут `from "react-dom/client"`. Тот же `react` может рисовать не браузер: React Native — другой рендерер. Для кафе нам нужен DOM.

Путать их вредно: «поставить только react» без `react-dom` в веб-проекте нельзя. Оба уже есть в шаблоне Vite.

## Библиотека, не платформа

React не обещает:

- маршруты (`/menu`, `/cart`);
- запрос к API;
- CSS-систему;
- сборку (это Vite);
- авторизацию.

Это нормально. Вы собираете стек сами или берёте метафреймворк, который уже выбрал за вас. Пока «Зёрнышко» живёт на одной странице — роутер не нужен. Когда страниц станет две, появится отдельный разговор.

Отсюда путаница «React vs Next». Next — рамка вокруг React: сервер, файлы-маршруты, иногда серверные компоненты. Изучать библиотеку внутри Next можно, но тогда непонятно, где кончается `createRoot`.

## SPA и сервер

Vite-приложение кафе — **SPA**: сервер отдаёт один HTML, дальше навигация и отрисовка — в браузере.

Серверный рендер (SSR) нужен, когда важны первый HTML для SEO, скорость первой отрисовки на слабом телефоне, контент до загрузки JS. Интернет-магазин с сотней посадочных — кандидат. Учебное меню на localhost — нет.

Не выбирайте Next «потому что так в вакансиях», пока не можете объяснить, какой кусок вам нужен сверх `createRoot`.

## Что React не заменяет

Можно написать меню кафе на чистом JS: шаблонные строки, `innerHTML`, слушатели. На трёх карточках это даже короче. Ломается на связях: бейдж «нет в наличии» должен погасить кнопку, счётчик заказа — совпасть с списком, цена — с количеством.

React выигрывает, когда связей много и экран — проекция данных. Если страница статическая («адрес и часы работы»), библиотека не обязательна.

## Кафе без React и с ним

Без библиотеки кнопка «В заказ» могла бы сделать так:

```js
count += 1;
document.querySelector(".order-count").textContent = String(count);
```

Пока счётчик один — работает. Когда то же число нужно в шапке, в корзине и на кнопке «оформить», вы копируете три правки и забываете четвёртую.

С React источник один — данные заказа. `OrderBar` и будущая шапка читают его и рисуют. Рассинхрон «в памяти 2, на экране 1» становится багом в данных, а не в трёх селекторах.

## Что запомнить

- Экран — функция данных, не набор DOM-мутаций.
- React сравнивает описания и патчит DOM; вам не нужно трогать узлы вручную.
- `react` — модель UI, `react-dom` — браузер.
- Vite-SPA достаточно, пока нет задачи серверного HTML.
