Компонент — функция с именем в PascalCase, которая возвращает описание UI. На middle-уровне важно отличать **функцию**, **элемент** и **дерево**, и знать, какие привычки ломают это дерево.

## Функция, элемент, DOM-узел

```jsx
function Header() {
  return <h1>Кафе «Зёрнышко»</h1>;
}

const element = <Header />;
```

- `Header` — тип, рецепт.
- `<Header />` — элемент: объект-описание «создай Header».
- Настоящий `<h1>` в документе появится, когда React применит дерево к DOM.

`<Header />` не вызывает функцию в тот же миг, как обычный `Header()`. React решает, когда вызывать, и может вызвать снова при обновлении данных. Поэтому компонент должен быть **предсказуемым**: одни и те же пропсы — то же описание.

## Зачем PascalCase

`header` — HTML. `Header` — ваш компонент. Если написать `<header />` маленькими, браузер получит семантический тег, не функцию. Если наоборот обернуть HTML в PascalCase без нужды — лишний слой.

Правило стабильное: **свои функции — с заглавной, стандартные теги — строчными**.

## Композиция вместо наследования

В ООП тянет сделать `class LatteCard extends DrinkCard`. В React так не делают. Карточка латте — это `DrinkCard` с другими данными, либо обёртка:

```jsx
function Menu() {
  return (
    <section>
      <h2>Меню</h2>
      <DrinkCard />
      <DrinkCard />
    </section>
  );
}
```

Позже внутрь `DrinkCard` придут пропсы (`name`, `price`). Ещё позже — `children`, если понадобится слот («бейдж сюда»). Общий принцип: **собрать из частей**, не строить иерархию классов.

`CafeApp` знает раскладку. `Header` знает заголовок. Никто не «наследует шапку».

## Чистота рендера

Тело компонента — не место для случайностей:

```jsx
let clicks = 0;

function OrderBar() {
  clicks += 1; // побочный эффект во время рендера
  return <p>Кликов: {clicks}</p>;
}
```

Строгий режим удвоит это, данные разъедутся, в продакшене число будет другим. Рендер читает пропсы и состояние и **возвращает JSX**. Менять внешние переменные, писать в localStorage, ходить на сервер — не здесь. Для этого будут события и эффекты.

Пока в «Зёрнышке» карточка всегда показывает латте — функция чистая: хоть десять раз вызови, описание одно.

## Компонент внутри компонента

Частая ловушка:

```jsx
function Menu() {
  function DrinkCard() {
    return <article>Латте</article>;
  }

  return (
    <section>
      <DrinkCard />
    </section>
  );
}
```

На каждый рендер `Menu` создаётся **новая** функция `DrinkCard`. Для React это другой тип компонента. Карточка размонтируется и смонтируется снова: состояние внутри (когда появится) сбросится, фокус потеряется, анимация моргнет.

Объявляйте `DrinkCard` рядом, на уровне модуля, не внутри `Menu`.

## Файлы

Пока три функции помещаются в `App.jsx` — так и держите. Когда файл перестаёт читаться, выносят:

```text
src/CafeApp.jsx
src/Header.jsx
src/Menu.jsx
src/DrinkCard.jsx
src/main.jsx
```

Имя файла обычно совпадает с компонентом. Главное — не прятать `DrinkCard` внутрь другой функции «чтобы не плодить файлы». Лучше один маленький файл, чем вложенное объявление.

## Экспорт

```jsx
export function Header() {
  return <h1>Кафе «Зёрнышко»</h1>;
}
```

Именованный экспорт проще искать и переименовывать. `export default` тоже работает; в одном файле не мешайте оба стиля без нужды. В треке дальше будем писать `export function …`.

## Классы — легаси

`class Menu extends React.Component` вы ещё встретите. Новый код кафе так не пишут: хуки живут в функциях, документация React — про функции. Понимать классы стоит, чтобы читать старый репозиторий, не чтобы начинать «Зёрнышко».

## Что запомнить

- Компонент — рецепт, `<Header />` — элемент, DOM — результат.
- Рендер чистый: без записи в внешний мир.
- Не объявляйте компоненты внутри компонентов.
- Сборка экрана — композиция функций, не наследование.
